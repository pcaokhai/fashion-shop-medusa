# Integration Specification — VNPay, bank-transfer (VietQR), GHN
Version 1.0 · 2026-09-29 · Owner: Tech lead · Normative sources: `contracts/openapi.yaml` (/hooks/*), `contracts/vnpay/`

Items marked **[verify]** MUST be confirmed against the provider sandbox and official docs in the named story; the
result is recorded as a fixture and, if behaviour differs, as a change to this document in the same PR.

## 1. Transport
| Provider | Direction | Transport | Auth |
| --- | --- | --- | --- |
| VNPay pay | browser redirect → VNPay | HTTPS GET query string | HMAC-SHA512 `vnp_SecureHash` |
| VNPay IPN | VNPay → `/hooks/vnpay/ipn` | HTTPS GET query string | same HMAC; source-IP allow-list optional |
| VNPay querydr/refund | backend → VNPay merchant API | HTTPS POST JSON | HMAC-SHA512 over pipe-joined fields **[verify VCK-204]** |
| Bank webhook | provider → `/hooks/vietqr` | HTTPS POST JSON | `Authorization: Apikey <token>` |
| GHN API | backend → GHN | HTTPS JSON | `Token` + `ShopId` headers |
| GHN webhook | GHN → `/hooks/ghn` | HTTPS POST JSON | shared token header (configured in GHN portal) **[verify VCK-403]** |
Max body 64 KB on hooks; TLS only in staging/production; hooks bypass CSRF and customer auth, never signature checks.

## 2. Identifiers and correlation
| Id | Assigned by | Format | Uniqueness / use |
| --- | --- | --- | --- |
| `TxnRef` | us | `VCK` + `yyyyMMdd` + 6 base32 chars (≤ 34 chars) | unique per payment attempt; one cart may have several |
| `vnp_TransactionNo` | VNPay | numeric | dedupe key with TxnRef |
| `TransferMemo` | us | `VCK` + 8 uppercase alnum (Crockford, no I/L/O/U) | unique per cart, expires with instruction |
| Bank txn `id` | provider | string | dedupe key |
| GHN `OrderCode` | GHN | string | links shipment ↔ fulfillment |
| `trace_id` | us | W3C traceparent | propagated to logs and outbound calls |

## 3. VNPay checksum rule
1. Take all `vnp_*` params except `vnp_SecureHash` and `vnp_SecureHashType`; drop empty values.
2. Sort by key (byte order). 3. Form-url-encode key and value (space → `+`), join `k=v` with `&`.
4. HMAC-SHA512 with the merchant hash secret; lowercase hex. Compare in constant time.
Golden vectors: `contracts/vnpay/golden-vectors.json` generated by `generate_vectors.py`. New edge case ⇒ new vector
first. **[verify VCK-203]** encoding of Vietnamese diacritics and `&` in `vnp_OrderInfo` (we send ASCII-only OrderInfo).

## 4. VNPay flows
### 4.1 Create payment (VCK-203)
Params: `vnp_Version=2.1.0`, `vnp_Command=pay`, `vnp_TmnCode`, `vnp_Amount = VND × 100`, `vnp_CurrCode=VND`,
`vnp_TxnRef`, `vnp_OrderInfo` (ASCII, ≤ 255), `vnp_OrderType=other`, `vnp_Locale=vn`, `vnp_ReturnUrl`, `vnp_IpAddr`,
`vnp_CreateDate` and `vnp_ExpireDate` (`yyyyMMddHHmmss`, GMT+7, expire = create + 15 min). A recon row
`PENDING_QUERY` with expected amount is written in the same workflow step that creates the TxnRef.

### 4.2 IPN handling (source of truth)
The handler MUST, in order: verify checksum (fail → `97`); find recon by TxnRef (none → `01`); if already
MATCHED/RESOLVED → `02`; compare `vnp_Amount/100` with expected (diff → `04`, recon MISMATCH `AMOUNT_DIFF`); then:
- `vnp_ResponseCode=00` and `vnp_TransactionStatus=00` → run `process-vnpay-ipn` (authorize + capture session,
  complete cart, recon MATCHED) → `00`.
- otherwise → mark attempt FAILED with code, keep cart open → `00` (acknowledged).
- unexpected error → `99` (VNPay may retry **[verify retry policy VCK-203]**).
It MUST NOT complete an order if the cart was cancelled or already completed by another TxnRef; instead recon
MISMATCH (`LATE_PAYMENT_AFTER_CANCEL` / `DUPLICATE_PAYMENT`) for admin refund.

### 4.3 Return URL
Browser lands on storefront `/checkout/vnpay-return`; storefront calls `verifyVnpayReturn`. Result is display-only:
PAID if the order already exists, PENDING_CONFIRMATION otherwise. MUST NOT mutate cart or order.

### 4.4 Reconciliation (VCK-204)
Job every 5 min: recon rows PENDING_QUERY older than 15 min (batch 100) → `querydr` → apply same rules as IPN.
After 24 h without a final status → MISMATCH `ORDER_NO_PAYMENT`, cart released.

### 4.5 Refund (VCK-205)
`command=refund`, `vnp_TransactionType` 02 (full) / 03 (partial) **[verify]**, `vnp_RequestId` unique per attempt and
reused on retry of the same attempt. Refund only for captured payments; amount ≤ captured − already refunded.

### 4.6 Response codes (display mapping)
| `vnp_ResponseCode` | Meaning | Storefront message |
| --- | --- | --- |
| 00 | Success | Thanh toán thành công |
| 07 | Success but flagged suspicious | Đang xác minh giao dịch (treated as PENDING, admin review) |
| 09 / 10 / 11 / 12 / 13 / 79 | Card/Internet banking issues, timeout, locked, wrong OTP/password | Thanh toán không thành công, vui lòng thử lại |
| 24 | Customer cancelled | Bạn đã huỷ thanh toán |
| 51 / 65 | Insufficient balance / daily limit | Tài khoản không đủ số dư hoặc vượt hạn mức |
| 75 | Bank under maintenance | Ngân hàng đang bảo trì |
| 99 | Other | Có lỗi xảy ra |
**[verify full list VCK-203]**

## 5. Bank transfer (VietQR) flow (VCK-604)
1. `getVietqrInstruction` issues a unique `TransferMemo`, amount, EMVCo payload; instruction expires in 30 min.
2. Provider webhook posts each incoming transaction. Matcher (pure function): normalise content (uppercase, strip
   diacritics/spaces) → regex `VCK[0-9A-HJKMNP-TV-Z]{8}` → find instruction → compare amount.
3. Exact amount → complete order, recon MATCHED. Under/over-payment or expired memo → MISMATCH for admin.
4. No memo match → store as UNMATCHED bank txn for manual assignment in the admin console.

## 6. GHN flows (VCK-402/403)
### 6.1 Quote
Input: warehouse ward code, destination ward code (2-tier, mapped via `vn_address.ghn_code`), weight/dimensions from
variants (defaults 300 g, 20×15×5 cm when missing). Timeout 3 s; failures return `TIMEOUT`/`UNAVAILABLE` per quote.

### 6.2 Create / cancel
Create on fulfillment creation with COD amount = order total for COD orders, 0 otherwise; store `OrderCode`
for compensation (cancel on workflow rollback).

### 6.3 Status mapping and state machine
| GHN status | Ours |
| --- | --- |
| ready_to_pick | CREATED |
| picking, money_collect_picking | PICKING |
| picked, storing, sorting | PICKED |
| transporting | IN_TRANSIT |
| delivering, money_collect_delivering | DELIVERING |
| delivered | DELIVERED |
| delivery_fail | DELIVERY_FAILED |
| waiting_to_return, return, return_transporting, return_sorting, returning | RETURNING |
| returned | RETURNED |
| cancel | CANCELLED |
| exception, damage, lost, return_fail | stays; raises admin alert |
Order of states: CREATED < PICKING < PICKED < IN_TRANSIT < DELIVERING < {DELIVERED | DELIVERY_FAILED}; DELIVERY_FAILED
→ DELIVERING allowed (re-attempt); RETURNING < RETURNED; CANCELLED terminal. Updates that move backwards are stored
as events but do not change current status. **[verify status list VCK-403]**

## 8. Security
Constant-time HMAC compare; secrets per environment; hooks log only ids and result codes; replaying a captured IPN
yields `02`; admin resolution requires `If-Match` version and writes AuditLog.

## 9. Change control
Any change here requires: vector/fixture update first, simulator update in `tools/sims`, contract tests green, and a
line in the next RELEASE note under "Integration changes".

## 10. Guest order access and OTP (VCK-406, ADR-014, docs/14)
```mermaid
sequenceDiagram
  participant B as Buyer (storefront)
  participant S as Store API (guest-order-access)
  participant R as Redis
  participant Z as ZNS / SMS
  B->>S: POST /store/order-lookup {display_id, phone}
  S->>R: rate-limit counters (IP, display id)
  S-->>B: 200 {token, masked order} | 404 generic (constant time) | 429 Retry-After/captcha
  B->>S: POST /session/cancel-otp (X-Order-Lookup-Token)
  S->>S: policy (pending + COD in v1) else 409 reason
  S->>R: challenge {codeHmac, attempts}
  S->>Z: OTP template (ZNS first, SMS fallback)
  B->>S: POST /session/cancel {challenge_id, otp, reason_code}
  S->>S: lock order row, re-check policy (staff confirm wins → 409)
  S-->>B: 200 cancelled; emit vck.order.guest_cancelled
```
ZNS OTP uses a dedicated approved template (id per environment); SMS fallback only if a brandname provider is
configured. OTP text never includes order contents. Delivery failures on all channels return 503
`upstream-unavailable` without consuming a send from the hourly cap.
